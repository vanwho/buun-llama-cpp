# 93-07 — Lock trim recovery and make the promotion diagnostic real

Revision: `hotpath-v10-20260914`. Amendment: `repair93-mtp-fast-20260922`.

Cluster: `repair93-mtp-diagnostics-v10`.

Execution model is pinned to `gpt-6-luna` at High reasoning for this task and
all retry assessments. Use only `gpt-6-luna` for this project; do not use
another model family.
Any successor tasks must carry the same exact model and assessment pins.

## Objective

Lock the 93-06 repair with a deterministic regression and correct the bounded
diagnostic so its cold rung can actually test cold-page promotion. The current
driver is capped at 4096 tokens, counts `args.repeats` for every rung (default
one request), and generates unrelated `cold-page-*` filler prompts. That
cannot perform the required A→B→A transition or prove return promotion.

## Work A — regression for the crash

1. Use the test-only rejection seam introduced by 93-06. Exercise at minimum:
   - target suffix trim rejected before mutation;
   - target trim succeeds and draft trim rejects;
   - target trim rejects after an allowed partial mutation, if the memory
     implementation can produce that outcome.
2. For each reachable case, assert the same final invariant: target and draft
   are both at the valid retained frontier or both empty; the slot ledger,
   speculative backup, checkpoint deliveries and cache-plan deliveries match
   that state; a subsequent request can safely run. No SIGSEGV/assertion and no
   success response may be emitted for a request whose state is invalid.
3. Prefer a focused test of the recovery coordinator using fake memory
   operations, plus one bounded server integration regression for the actual
   prompt-trim caller if the seam permits. Do not create a broad synthetic
   benchmark or a production failure-injection flag.

## Work B — correct diagnostic bounds and cold sequence

1. In `tools/server/bench/mtp_diagnostic.py` and
   `tools/server/bench/run-mtp-diagnostic.py`, keep the default context at
   4096 but permit a validated maximum of 16384. Validate that the *actual
   rendered/tokenized input for each request* is no greater than 16384 tokens
   and fits `context - n_predict`; record the exact token count. Never silently
   truncate. Add a contract test at the limit and one token over it.
2. Keep target hot KV at or below 49152 tokens in the contract. Validate
   `hot_pages * page_size_tokens <= 49152`, and require the selected route to
   pass `--kv-safety-headroom auto` (or the canonical runner's equivalent).
   In `run-mtp-diagnostic.py::adapter_command` and
   `run_canonical_adapter`, forward this value into the canonical profile
   runner and environment; include it in `identity_errors` and the saved rung
   identity so a stale service override cannot pass as the requested setup.
   Record observed usable/free/headroom/scratch values and reject a rung before
   loading if its requested pages violate the allocator budget. Do not treat
   48K as a requested default: retain the present 16-page resident and 4-page
   cold test sizes.
3. Fix `request_contract.context_tokens` to record `args.context`, not the
   global maximum constant. Ensure each exact command and process identity
   includes the effective `-c`, `-b`, `-ub`, `--kv-hot-pages`, safety headroom,
   target/draft Turbo4 types, and GPU draft placement.
   Support per-rung context without raising the default: use 4096 for dense
   and resident controls and 8192 only for the cold sequence. Refuse any
   configured context above 16384. Before every direct request, call the
   candidate's `/tokenize` endpoint with the exact raw `/completion` prompt,
   record returned token count, and refuse to send if it exceeds 16384 or
   `context - n_predict`. Record configured context separately from actual
   rendered prompt tokens.
4. Change only the cold-promotion rung to run its required three sequential,
   prefix-preserving requests even when `--repeats=1`; retain the existing
   repeat limit for other rungs. Use real short labeled documents:
   - request 1 ingests DOCUMENT_A and asks a unique fact from A;
   - request 2 appends DOCUMENT_B, asks a unique fact from B, and is long
     enough that A's relevant page is outside the four-page hot set;
   - request 3 appends a query for A's unique fact, causing A to be selected
     from cold host backing.
   Each rendered prefix plus generation reserve must fit the configured
   context; set the cold control to `-c 8192`, four hot pages (1024 tokens),
   one slot, `-b 128 -ub 64`, `pin_recent=0`, and at most 16 output tokens.
5. Extend `tools/server/bench/validate-mtp-post-repair.py` (or its focused
   successor) to require the three request order/identity fields and real
   movement proof: A page is cold before request 3; request 3 selects the same
   logical page generation/content version; H2D completes; mapping/table
   publication occurs before graph consumption; both target and draft consume
   the page. Missing events remain null and fail promotion. `selected direct`
   or `selected packed` without this chain is not promotion.
6. Keep the existing MTP request-local denominator logic. Never calculate
   acceptance from `accepted_target_tokens`; never merge counters between
   requests or rungs. Keep `selected_reference` refused for acceptance.
