## Objective

Measure whether selected Turbo4 target KV with a 4K GPU hot set, CPU-RAM
Turbo4 target-KV offload, and dense GPU Turbo4 target KV have different
prefill/decode performance while native MTP remains entirely GPU-resident
Turbo4. Unlike 93-11f, every request here must contain a verified logical KV
working set larger than the 4K selected hot capacity, so selected-vs-CPU speed
is not inferred from a resident-only request. The minimum objective is at
least 500 tok/s median on freshly evaluated selected-page prefill for each
canonical prompt; 750 tok/s is preferred. Below 500, or no faster than
CPU-RAM, is a missed goal that triggers the specified diagnosis/change/retest
loop and concrete dependent remediation tasks before any final-goal claim.

This is a bounded 8K-context comparative screen, not a 256K occupancy test or
the final context-speed curve. The 500 tok/s selected-prefill floor is a real
gate, not a reporting-only finding. The 750 tok/s value is the preferred
target; report any gap without relaxing the floor.

## Required selected-prefill optimization loop

Before the final matrix, keep B=1024/U=256, context 8,192, hot budget
4,096, direct selected-packed route, Turbo4 target K/V, GPU Turbo4 draft K/V,
`draft_n_max=2`, the same three fixture-backed inputs, and thinking off fixed.
Each rendered input must be 4,352–8,192 tokens; no prefill request may exceed
16,384 tokens.

1. Capture a selected-pager baseline with one 40-token warmup and one
   400-token measured fresh-prefill request per prompt. Clear or disable
   prompt-prefix reuse so the number of freshly evaluated tokens equals the
   full rendered input. Preserve exact request bytes, token count, prefill
   milliseconds, candidate hash, effective route and B/U, request-local
   transfer/wait/fault counters, CPU time, and a coarse out-of-band GPU
   utilization/power sample. Do not add per-token telemetry to the hot path.
2. After measuring, explicitly reassess each prompt: compare dense-GPU
   reference prefill (ordinary operation is expected around 1,300–1,500
   tok/s) and CPU-RAM; verify the direct selected route, effective geometry,
   cache accounting, and actual evaluated token count; classify the limit as
   GPU occupancy/work, selected-kernel/tile efficiency, host synchronization
   or transfer, prompt-cache accounting, or setup/measurement error. Low GPU
   power alone is not a diagnosis.
3. If selected prefill is below 500 tok/s for any prompt or not faster than
   CPU-RAM, write one source-backed hypothesis, make one narrowly scoped
   implementation or demonstrated setup fix, run the smallest relevant build
   and regression checks, then repeat the exact same one-request-per-prompt
   screen on the resulting immutable candidate. Record before/after rates,
   source paths, candidate hashes, test commands/results, and why the change
   did or did not help. Do not change batch geometry, context, inputs, output
   cap, MTP placement/type, hot budget, or route to improve the number.
4. Repeat assess → one change → focused test → identical measurement until all
   three prompt rates are at least 500 tok/s and faster than the paired
   CPU-RAM medians, or three distinct evidence-supported changes have been
   tested. Treat setup errors separately: repair and repeat them; they do not
   consume an optimization attempt. 750 tok/s is the preferred target but
   not a reason to continue speculative changes after all three meet 500.
5. Run the final paired matrix only on the final candidate. Each measured row
   must report `full_rendered_tokens`, `fresh_prefill_tokens`,
   `cached_prefix_tokens`, and `fresh_prefill_ms`; require fresh tokens equal
   full rendered tokens, cached tokens equal zero, and `prompt_tps` to equal
   fresh tokens divided by fresh-prefill seconds within 5%. Retain every
   iteration including regressions. If the floor is still missed after three
   valid changes, record a failed speed gate and the failed hypotheses; do
   not declare success. The 93-13 review must create specific implementation
   and rebenchmark successors before claiming the goal.

Do not use these runs to retune B/U: every placement and iteration uses
