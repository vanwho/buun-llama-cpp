## Required assessment method

1. Verify the incoming range SHA and final merged candidate SHA match 93-11i.
   Derive the exact incoming commits from its pre-merge HEAD and fetched
   `origin/master` SHA; do not silently assess a different range.
2. Triage only changed commits/files that touch one or more of these areas:
   - prompt ingest/prefill batching, graph construction/reuse, Flash Attention,
     CUDA launch/tile/chunk behavior, and avoiding per-token host synchronization;
   - Turbo4/TurboQuant KV layouts, dequantization, packed-kernel dispatch, and
     CPU-RAM backing/transfer overlap;
   - MTP draft-KV placement, verify graph, checkpoints/rollback, and cache
     identity across retained/prefilled context;
   - Qwen3.8 architecture/window handling or server prompt-cache behavior that
     directly affects the fixed file-backed A→B→A workload.
3. For each candidate change, record commit, changed paths/symbols, upstream
   behavior, current fork behavior, applicability to the 16GB RTX 4080 and
   portable backends, expected speed/correctness effect, compatibility risk,
   and a small falsifiable test. Categorize as `adopt`, `adapt`, `defer`, or
   `not_relevant`; cite exact code paths and evidence, not a commit subject
   alone.
4. Do not select an approach merely because it is newer/upstream. Reject
   paths that move MTP/KV to CPU, use `selected_reference`, gather the entire
   selected cache to F16, add synchronous per-token selector/statistics work,
   or change Turbo4 formats without evidence that they preserve the required
   GPU-resident Turbo4 behavior.
5. For each `adopt` or `adapt`, create a concrete implementation task before
   93-11k (and therefore before 93-12). Include exact file/function pointers,
   implementation boundaries, regression test expected to fail before the
   change, bounded context files, fixed benchmark, dependencies, and rollback
   criteria. Task state must use `gpt-6-luna`; choose High unless the change
   truly requires XHigh. The new task must not change the locked benchmark
   geometry B=1024/U=256.
6. If no upstream item applies, record a concise rationale and leave the
   sequence unchanged. Do not invent work to justify the review task.
7. Update only the task graph/packets needed for concrete adopted changes;
   preserve the in-progress state of unrelated tasks. Each created task must
   be inserted in execution order, have a packet, required proof, completion
   check, and dependencies, and precede 93-11k/93-12. Do not mark an
   unimplemented optimization complete.
8. Produce `handoffs/93-11j.md` and `evidence/V10_93-11j.json`. Include the
   exact incoming range, a compact relevance table, links to created tasks or
   the no-change rationale, merged candidate hash, and raw analysis/build
   artifact digests. The final disposition must explicitly say whether 93-12
   can proceed on the current candidate or must wait for named tasks.
