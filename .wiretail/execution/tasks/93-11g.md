## Position and objective

Run this task immediately after 93-11f and before 93-12 or any later
phase-93 benchmark. The retired 93-11e packet is not a prerequisite or a
separate follow-up. Replace the old tiny inline A/B/A example with a real-file
retrieval campaign that proves a cold file page is automatically selected and
promoted when a later prompt asks about that file.

Use the 24 files under
`tools/server/bench/fixtures/pager-promotion/`: eight distinct Python merge
scripts, eight mmap-versus-read explanations, and eight Bash directory-watch
scripts. Each fixture is exactly 1,024 Qwen3.8-27B tokenizer tokens when read
without BOS; `manifest.json` records its ID, token count, retrieval fact, and
SHA-256. The full rendered prompt has extra separators, questions, chat/special
tokens, and retained prefix, so tokenize every complete request with the
candidate server before sending it.

This is a paging/promotion functional campaign, not the 93-11f speed benchmark.
Set the actual llama-server context to `-c 8192` and the ordinary automatic
target-KV GPU hot-residency budget to 4,096 tokens (16 pages × 256). Keep the
full A→B→A prompt below the server's 8,192-token context limit while its live
KV footprint exceeds the 4,096-token hot budget. The normal pager must then
evict A from GPU residency because of hot-budget pressure and later promote it
when A is naturally queried again. This tests standard server/pager behavior:
do not exceed `-c 8192`, cause context shifting, or use any test-only/manual
page eviction, page selection, or promotion operation. The 49,152-token limit
is only an absolute phase-93 ceiling; do not raise this test's context or hot
set to that ceiling.

  candidate built from the current task source. Verify the managed process

  size 256, ordinary automatic target-KV GPU hot budget 16 pages / 4,096
  tokens, one slot, `-b 128 -ub 64`, `--kv-pin-recent 0`, and automatic
  safety headroom. Verify and record the live process command plus the
  allocator-admitted context and hot bytes/tokens; requested settings alone
  are not proof. If headroom requires lowering hot pages, stop and revise this
  task's test geometry before requests; do not silently call a different
  geometry 8K/4K.

  request. No request may name a page, set route/selector overrides, adjust

## Required same-slot sequence

Use `pager_promotion.py` as the single source of fixture order, neutral A
questions, B/A-again questions, and local expected answers; do not duplicate
or hand-edit prompt strings in the live driver. Build each live case with
`build_promotion_steps`. For each step, call `messages_for_step(steps, index,
prior_actual_replies)`; this returns the cumulative same-slot chat messages
and rejects a prior server reply that did not match its local expected answer.
After a response, validate it before appending the actual response text to
`prior_actual_replies`. Never inject a manifest expectation as a simulated
assistant response in a live request.

Load fixture **contents**, not file paths, as ordinary user messages in the
same live slot. Preserve every prior user/assistant turn exactly, and set
prompt caching on continuation requests. Fixture IDs appear only in the
fixture's original body, ordinary manifest question text, and local evidence;
never send page numbers/IDs, route overrides, or any separate pager-selection
hint. The expected answer for the current request remains local-only and is
not added to that request's user content.

For each messages array, use `ServerPromptRenderer` from
`tools/server/bench/prompt_sizing.py` against the verified candidate to call
`/apply-template` and `/tokenize` on the exact server-rendered prompt. Persist
the original messages, rendered prompt, token IDs/count, template identity,
and raw endpoint responses. Send those same messages to the candidate's
`/v1/chat/completions`; do not re-render with a local or hardcoded Qwen
template. Reject before generation if rendered prompt tokens plus
`n_predict` exceed 8,192 or the required reserve.

Run every one of the 24 fixture files once as target A, grouped by family.
Before each independent target case, erase the single test slot with
`POST /slots/<slot-id>?action=erase`; verify the slot has zero live prompt rows,
but do not restart/unload the server. For each target, select four
deterministic, different same-family fixture files as later B documents
(walk forward cyclically through that family's manifest order, skipping A).
The base case is six requests: one A query, one turn for each B file, and one
A-again query. Execute these sequential requests:

1. Append the complete A file body and a neutral category question that does
   **not** reveal or ask for A's `retrieval_key`; require exactly `YES`. Use
   the matching question form: Python: "Does this file define a callable
   `merge_sorted` function?" Markdown: "Does this file compare `mmap` and
   `read`?" Bash: "Does this file watch a directory for new files?" This
   makes A relevant without placing its target answer in an earlier response.
2. Append B1, B2, B3, and B4 one at a time, each as the next full prefix, and
   ask for that B file's manifest retrieval fact. Require the expected short
   answer for each B before continuing. This focuses the recent requests on
   newer files while retaining A in the same context.
3. Keep every complete rendered request within `-c 8192`; reject a sequence
   that would trigger server context shifting or discard old prompt rows.
   The sequence must create pressure by retaining A in the logical context
   while ordinary automatic residency exceeds the 4,096-token GPU hot budget.
   Immediately before the final A-again request, capture a request-local page
   snapshot and require A's source logical page(s) to be complete and
   host-backed/nonresident. If A remains resident, append additional
   same-family B files as ordinary user-context turns, asking their own
   retrieval facts, up to six B files total, and re-check. This is additional
   natural workload pressure, not a forced eviction. Pre-tokenize every
   resulting full prompt; it must remain within `8192 - n_predict` tokens.
   Obtain any B5/B6 turn from `build_promotion_steps(..., b_count=5|6)` and
   pass the four or five actual validated replies already observed to
   `messages_for_step`; never restart the sequence to add more pressure.
   If A cannot be made cold while retaining it in the logical context under
   the verified 8K/4K geometry, diagnose/repair the normal residency policy in
   this task; do not claim a promotion test based on a still-hot A or a context
   shift that discarded A.
4. Append the manifest question for A's unique retrieval fact. Require an
   exact normalized match to the manifest answer. Do not tell the selector
   which page to fetch.

The initial A question must not disclose the retrieval key, and none of the B
answers may equal A's key. This prevents a correct final answer from being
explained by an answer already present in prior assistant output. The final
request must use the same slot, model, candidate, and growing prefix as the
ingest requests.

Before each live completion, call the candidate's tokenizer endpoint on the
exact server-rendered prompt with special-token parsing enabled through the
renderer described above. Persist the request bytes and tokenizer response;
refuse an over-context prompt instead of truncating, shifting, or silently
lowering context. Preserve each request's raw response, before/after slot
snapshots, pager metrics, MTP draft/accept counters, and candidate identity.

## Required natural promotion proof

For **each** of the 24 A-again requests, capture request-correlated facts and
require this ordered chain for the same logical page, page generation, and
content version:

1. A page is complete and host-backed/nonresident immediately before A-again.
2. The normal attention selector nominates that same page from A's natural
   query; there is no client choice, forced-page option, route override, or
   reference path.
3. H2D for the same page is submitted and completes.
4. The device mapping/table publication for that generation completes after
   H2D and before attention consumes the mapping.
5. Target attention consumes the promoted page, and native MTP draft
   verification consumes the corresponding page from its own GPU Turbo4
   cache.
6. The request returns A's exact expected retrieval fact.

Correlate each event to request ID, logical page, generation/content version,
and monotonic event sequence. A global positive H2D total, successful HTTP
status, positive draft-token count, selected page list, or correct answer by
itself is not promotion proof. If the current backend does not export a needed
page/event boundary, add the smallest bounded transaction/event-level
diagnostic at the promotion/publication/consumer boundary; do not add
per-token logging, a new attention route, or synchronization to the hot
request loop. Add deterministic extraction/order tests that reject missing,
stale, mismatched, and out-of-order events.

## Failure handling and iteration

- Keep a progress record after each target file so an interrupted campaign
  resumes from the first unverified file without replaying completed targets.
- On a setup error, repair the candidate invocation, permissions, context
  arithmetic, or managed service identity in this task and repeat the affected
  target. Do not record `not_measured` and advance.
- On a runtime defect, preserve the raw failing request and exact event/page
  boundary, trace to the first failing owner, make the smallest source repair,
  rebuild one immutable candidate, rerun focused deterministic tests, then
  repeat the affected target and all targets that share the repaired owner.
- Keep test loops bounded: four B documents initially, at most six only when
  needed to establish cold state; one 16-token-or-less generation per request;
  no long corpus generation or 400-token speed measurement here.
- If the full 24-target sweep exposes an implementation repair that cannot be
  safely completed within this packet, add its narrowly scoped repair task
  immediately before 93-12, set this task and 93-12 to depend on it, and keep
  the downstream benchmark tasks gated. Do not pass merely because fixture
  files or deterministic unit tests exist. 93-11g itself remains the sole
  owner of this proof even if implementation is delegated to a successor.
