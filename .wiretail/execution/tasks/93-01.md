# 93-01 — Build the bounded MTP diagnostic harness and controls

Revision: `mtp-diagnostic-v10-20260922`. Amendment: `repair93-mtp-fast-20260922`.

Cluster: `repair93-mtp-diagnostics-v10`.

## Objective

Replace the old long frontier probe with a reproducible, short comparison that
can tell whether MTP is failing before paging is involved. Do not attempt a
full-L occupancy run, context curve, or speed campaign.

## Read and inspect

- `.wiretail/execution/clusters/repair93-mtp-diagnostics-v10.md`
- `.wiretail/execution/v10/REPAIR85_PLAN.md`, `REPAIR85_TESTING.md`, and the
  phase-88/89 MTP summaries
- `tools/server/bench/run-pager-profile-benchmark.py` and its contract helper
- `tools/server/server-context.cpp` MTP option/configuration handling
- `src/llama-kv-attention-execution.cpp` route planning and route counters
- the existing MTP request/slot metrics and focused CUDA tests

## Work

1. Create or extend one bounded diagnostic driver under the repository's
   existing benchmark/test directories. It must run at most three short
   requests per rung, use `n_predict`/completion length no greater than 16,
   draft n-max 2, and a total context no greater than 4096 unless a smaller
   context is required by available VRAM. Use the canonical Qwen3.8-27B
   UD-IQ4_XS model, `-ctk turbo4 -ctv turbo4`, `-ctkd turbo4 -ctvd turbo4`,
   and explicit GPU draft placement.
2. Make the driver execute these rungs in order: MTP-off dense/all-GPU;
   MTP-on dense/all-GPU; MTP-on selected/paged with all logical pages
   resident; and one separate tiny-hot-set cold-page promotion probe. Keep
   each rung in a separate raw directory and never combine counters across
   rungs.
3. Before each request, record model/binary hashes, exact command line, target
   and draft context sizes, batch/ubatch, MTP placement and cache types, route
   policy, hot-page budget, and free VRAM. After each request retain the raw
   SSE/JSON response, server log, `/slots` snapshot, and metrics before/after.
4. Require request-level fields for `draft_n`, `draft_n_accepted`, accepted
   tokens, verification steps, target/draft positions, rollback/rewind count,
   pager route, page-table epoch, and MTP K/V placement/types. Missing fields
   must fail the rung as an evidence-contract error, not be converted to zero.
5. Refuse to score any rung whose route is `selected_reference`, CPU attention,
   CPU draft K/V, non-Turbo4 K/V, or a different endpoint process than the
   recorded candidate binary. Repair the launcher/configuration and rerun the
   short rung when this is a setup error.

## Acceptance

The four-rung harness runs without a long polling loop, produces immutable raw
receipts, and clearly identifies the first rung with low acceptance. It must
prove whether MTP placement is GPU/Turbo4 independently of whether acceptance
is good. No claim about 256K occupancy or production speed is allowed.

## Deliverable

Create `handoffs/93-01.md`, `evidence/V10_93-01.json`, a compact Markdown
summary, and the raw diagnostic roots. Include an explicit `first_bad_rung`
and `setup_failure` field when applicable.
