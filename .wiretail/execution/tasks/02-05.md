# 02-05 — Prove canonical host backing with a fixed GPU window

## Objective

Establish real 256K Turbo4 target storage with canonical host copies for sealed pages and a bounded,
fixed/manual 304-page GPU working set before adding attention-driven selection or a custom paged kernel.

## Read

- `CONTRIBUTING.md`, any current `AGENTS.md`, task README, and plan sections 3.1, 3.2, 8.1–8.5, 8.8,
  9.1–9.3, and Phase 02.
- Handoffs and tests from 01-02, 01-03, and 02-01 through 02-04.
- Current KV commit/mutation paths, VBR VMM helpers, selected capture/adoption code, pinned-ring limits,
  host catalog accounting, and CUDA transfer/event APIs.

## Fixed-window contract

- A cross-layer logical page is 256 positions and contains Turbo4 K+V segments for all 16 target
  attention layers; geometry is derived and validated, never assumed silently.
- The current partial page is GPU-authoritative, pinned, and not evictable.
- At page seal, issue one logical batched D2H transaction for every layer/side segment. Publish the host
  handle only after all segments, checksums, identities, and generations validate.
- Once sealed, the host copy is canonical. Normal eviction of a clean resident page drops/unmaps the GPU
  slot without D2H. Any later mutation invalidates or dirties the host generation and must reseal before
  eviction.
- Promotion copies opaque Turbo4 bytes H2D through a bounded pinned ring and becomes visible only via an
  atomic residency-table publication after its completion event.
- Allocate at most the admitted physical rows/slots plus staging and explicit headroom. A hidden full
  262K target GPU tensor fails the task even if VMM reports few committed bytes.

## Implementation steps

1. Wire page-seal detection to the selected capture transaction; cover the final partial page with an
   explicit seal/valid-row mask for checkpoint or attention use.
2. Add a test/debug fixed selector (for example newest 304 pages plus explicit logical page IDs) behind
   internal experimental configuration; do not add policy scoring.
3. Fill logical pages, seal host backing, promote selected pages, evict clean pages without D2H, restore
   them, and reconcile forward/reverse maps and byte ledgers after each transaction.
4. Use separate compute and upload streams/events where supported. No published slot may be overwritten
   until its consumer fence completes.
5. Emit counters for seal D2H, normal-eviction D2H, promotion H2D, useful/actual bytes, resident pages,
   host-valid pages, pinned pages, staging bytes, and stale completion rejects.

## Tests and acceptance

- Fake-backend tests cover full page, partial tail, seal failure at every segment, checksum mismatch,
  stale generation, mutation/reseal, all-pinned exhaustion, host-budget exhaustion, and teardown.
- Assert that a sealed clean eviction increments no D2H byte/copy counter.
- For Qwen3.8 geometry, assert 4.125 MiB/page, 1,024 logical pages, 304 admitted slots near the reference
  budget, 4.125 GiB full host payload at completion, and bounded GPU physical allocation. Use actual row
  sizes and report any disagreement rather than hardcoding acceptance.
- On reference CUDA, run fill/seal/promote/evict/restore checksums with a deterministic fixed window and
  preserve allocation/transfer telemetry. Attention output is not yet an acceptance criterion.

## Stop conditions

Block on unbounded host vectors, synchronous per-segment waits on the decode path, a required full-size
GPU target tensor, failed rollback, or inability to distinguish seal D2H from eviction D2H. Do not begin
custom FA, telemetry scoring, or dynamic policy in this task.

## Handoff

Record the state-transition trace, exact allocations, copy batches/events, ledger reconciliation,
failure-injection results, CUDA artifact paths, and the manual page set used.
