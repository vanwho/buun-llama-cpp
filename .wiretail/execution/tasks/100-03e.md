## Goal and exact code owners

The 100-03b cumulative counters suggest packing, graph churn and host sealing,
but cannot allocate the ~180 tok/s wall time. Add *diagnostic-only* timing
around `llm_graph_input_attn_kv::refresh_selected_data` and graph reuse/build
in `src/llama-graph.cpp`, `llama_kv_attention_packed_cache::find_or_create`
and `select_route` in `src/llama-kv-attention-execution.cpp`,
`llama_kv_cache::seal_kv_pager_pages`/`apply_pager_live_policy`, and the
host-capture enqueue/wait/completion in `src/llama-kv-pager.cpp`. Inspect the
post-merge equivalent symbols if moved. Also time scheduler/graph execution
and query checkpoint/replay in `src/llama-context.cpp` and
`tools/server/server-context.cpp`. Keep GPU kernel timing separate from CPU
wall time; use CUDA events only in explicit profiling mode, never a device
synchronize per page/ubatch in ordinary inference.

## Procedure

1. Produce a request-local counter baseline and post-request delta, not
   lifetime totals. Include fresh input tokens, selected rows/pages, packed
   bytes/rows copied (history vs current append), graph reuse/rebuild *reason*
   (`row_capacity`, physical key, content key, ubatch shape, source lifetime),
   A owner allocations/drains/bytes, seal pages and useful D2H bytes, queue
   waits, selector/promotion H2D, replay count, output tokens, MTP
   drafted/accepted, route and fallback reason. Use bounded integer counters
   and at most one compact event per request in profiling mode. Existing
   metrics may be reused rather than duplicated.
2. Run exactly one authenticated fresh canonical prompt-2 request with the
   post-merge binary, L8192/H4096, page256, B1024/U256, target/draft Turbo4,
   native GPU MTP nmax2, reasoning off. Ask for at most 80 output tokens;
   measure fresh prefill and decode separately. Capture a second *same-profile*
   no-edit request only if needed to separate first graph capture from steady
   reuse. No 36-row campaign, full-context fill, or second Qwen process.
3. Produce `phase_us` with disjoint or explicitly overlapping categories and
   a reconciliation to request wall time. Report which category is largest;
   if profiling itself is material, report diagnostic-on/off deltas and turn
   counters off after the run. Preserve GPU utilization/power sample if
   available. Never infer bottleneck from the lifetime counters alone.
4. Add a small deterministic counter/reset/graph-reason fixture. Its pass,
   plus the one raw request and candidate identity, is proof
   `request_local_hotpath_attribution`; write V10 receipt and handoff. On
   auth/identity/launch failure repair setup and repeat only this one row.
