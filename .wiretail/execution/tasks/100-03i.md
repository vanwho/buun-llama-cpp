# 100-03i — Small matched speed decision and repair scheduling

Revision: `hotpath-v10-20260914`. Amendment: `post100-hotpath-20260930`.
Cluster: `forward100-final`. Model and assessments: `gpt-6-luna`, High.
Dependency: `100-03h`. This is the only canonical speed campaign after the
merge/hot-path edits and before integrated proof 100-04. It may report a
measured miss; it cannot call one probe a goal pass.

## Candidate and workload

Use one executable/DSO/model/source identity and the same rendered prompt and
fresh-slot semantics for selected GPU-hot/CPU-host, ordinary CPU-main-KV
control, and dense/all-resident GPU only when the latter is actually feasible
at the matched C. L8192/H4096, page256, B1024/U256, target/draft Turbo4,
native full-L GPU MTP, nmax2, temperature 0, reasoning off for selected.
Keep any non-Turbo4 CPU control codec explicitly labeled; do not invent CPU
Turbo4 execution. Record actual C>H if measuring physical offload. Never
load two 27B services simultaneously; use the managed lifecycle and verify
argv/loaded binaries after every switch. Retain the successful selected
candidate loaded after the control sequence.

Exact prompts, in order:

1. `write a python function that merges two sorted lists into one sorted list, with docstring.`
2. `explain the difference between mmap and read for loading large files, one paragraph.`
3. `write a bash script that watches a directory and prints new files as they appear.`

One 40-output-token warmup, then **three measured requests per prompt** with
400 requested output tokens, for each feasible placement. EOG may finish
early; record actual output token count. This is at most 27 measured requests,
not an open-ended 36/48-row retest loop. A config/auth/identity failure is
fixed and just that row repeated; a slow progressing request is stopped after
one representative chunk and attributed, not allowed to crawl for hours.
Use the already prepared corpus/prefix from the 100-03b handoff to produce
actual cold host-backed C>H. Do not count cached-prefix tokens as fresh
prefill. Preserve raw request, per-request metrics delta, hashes and pairing.

## Report and decision

Report per prompt median fresh prefill and decode tok/s, TTFT, actual MTP
accepted/drafted, CPU/GPU useful bytes, H2D/D2H, faults, evictions, selected
pages, graph captures/owner replacements, packed copied rows, query replay,
peak A/H/draft/scratch VRAM, RAM, GPU power/utilization and errors. Give
selected/CPU decode and selected/dense prompt ratios only for genuinely paired
rows. Compare to user targets: selected fresh prefill >=500 tok/s per prompt
(750 preferred), MTP acceptance >=75/40/60% for prompts 1/2/3, positive
selected decode advantage over ordinary CPU-KV, no per-output historical H2D.
Do not make 3x/5x an automatic task-completion trap; show those as goals.

If a goal misses: this measurement task can complete with `goal_miss`, but
**before marking it done** insert a source-directed remediation successor for the
largest *request-local* cost or first state divergence. The new packet must
name owner/symbol, exact defect hypothesis, one focused fixture, one short
retake, and dependency; update 100-04 to depend on the successor. No generic
"audit again" or unchanged campaign. If attribution points to irreducible
Turbo4 D2H/BW or sparse-target/dense-draft divergence, quantify that honestly
and choose a different bounded GPU route/selection policy only after a paired
microprobe. No relaxing the performance goal to pass a receipt.

Proof `short_matched_speed_decision` is valid hashed rows and a faithful
goal_pass/goal_miss decision, *not* a numeric pass requirement. Write
`goal_status: pass` or `goal_status: miss` plus per-prompt measured values in
`SHORT_PATH_POSTMERGE.json`; only `pass` releases the 101-01 speed gate.
Receipt
`evidence/V10_100-03i.json`; summary `evidence/SHORT_PATH_POSTMERGE.md/json`;
handoff and raw root under 100-03i. There is no 256K curve here; phase 101
owns occupancy only after correctness and source-directed speed progress.
