## Objective

Create the first comparable repo-content benchmark at L=16384/H=8192 using the
checked-in A→B→A source/document prompts in
`tools/server/bench/fixtures/repo-context-v1/`. Compare target KV entirely on
GPU, target KV entirely host-resident, and selected GPU-hot/CPU-host paging.
The model execution and native MTP draft stay on CUDA/GPU in all three rows;
“CPU” means the target KV placement control, not CPU-only model inference.
Do not run this task at a different logical context. The prior L=8192 attempt
is retained as a failed-fit diagnostic: the complete mandatory A/B/A history
and answer/replay reserve required 10,829 tokens, so 8K cannot host this
fixture without trimming or changing prompts. L=16,384 is the smallest
page-aligned stage that preserves the full fixture and leaves room for actual
host-backed pages.

The repo-content helper, A/B/A driver and initial tests already exist from
the previous attempts. On the next run, do not restart implementation from
scratch: inspect those current files, run the focused tests, then invoke
`run-repo-context-baseline.py --preflight-only` on the already verified
full-GPU L=16,384 candidate. This must report zero generation requests and a
passing complete A/B/A reserve. If it passes, proceed directly into the three
required placement baselines. Edit existing code only for a reproduced defect
or to implement the explicit boundary/telemetry checks below.

This is both a small benchmark baseline and a natural retrieval observation.
It must capture actual per-turn speed/MTP and the complete cold→nomination→
admission→H2D→publication→target-use chain when selected paging naturally does
those transitions. Do not force selection or infer promotion from an answer.
Missing promotion telemetry is a measured finding, not permission to fabricate
a pass or to stop collecting the remaining rows.

## Fixed runtime matrix

Use the same built binary, Qwen3.8-27B UD-IQ4_XS model, prompt files, logical
L=16384, page size 256, B=1024/U=256, one slot, sampler and request budgets in
all rows. MTP is always enabled: draft context L=16384, draft placement GPU,
draft K/V Turbo4, `draft_n_max=2`; target K/V is Turbo4 wherever that target
placement supports it. Reasoning/thinking is off. Do not change B/U, threads,
batching, model, or other server settings between rows.

Run these target-KV placement rows:

- **GPU resident:** full target KV resident on GPU for this small-L control;
- **host resident:** existing ordinary CPU/host target-KV offload control,
  with model execution and Turbo4 MTP still on GPU. Record its actual target
  KV type. If CPU Turbo4 attention is unsupported, use only the existing
  supported ordinary cache type and label it honestly; do not add a CPU
  TurboQuant implementation for this benchmark;
- **selected:** H=8192 GPU-hot target tokens with canonical host backing for
  the remainder. This is the only row that claims selected paging.

Run rows in this order: full-GPU target KV, full-host/CPU target KV, selected
GPU-hot/host-backed target KV. The first two are required matched baseline
controls, not optional admission checks. In the host row, CPU refers only to
target-KV residency; CUDA model execution and full-L GPU Turbo4 MTP remain on.
Run one warm-up A→B→A sequence and three measured A→B→A
sequences with `max_tokens=400` on every answer, resetting
the same slot through the existing lifecycle between sequences. Capture
request-local prefill/decode/TTFT/MTP and page-state/transfer telemetry for all
three turns. MTP median floor is 40% per prompt-role across the three measured
sequences; if a row misses, report the miss and continue the other configurations
because the benchmark is meant to establish context-conditioned rates. Do not
use the MTP miss alone to block occupancy follow-up.

If the selected row OOMs, lower only H in 256-token page-aligned steps,
keeping L=16384, B/U, batch, model, MTP, cache types and every other server
setting unchanged; rerun all three placement rows at the same fixed settings
where the comparison remains meaningful, and record the changed H. Do not
lower L or B/U to manufacture a pass. Setup/identity failures must be repaired
and the affected sequence repeated. Pass a changed selected capacity through
`run-repo-context-baseline.py --hot-tokens`; the runner must reject a server
whose effective selected page count does not match that value. All rows still
use the same content frontier and L; only selected H may change under this
OOM rule.
