## Ordered implementation / experiment

1. Use the release's full-context configuration with full GPU Turbo4 MTP. Ensure actual occupied pages exceed safe hot capacity; if not, lower only the explicit test hot-byte cap and document it.

2. Run warm focus, cold old-page retrieval, multi-hop focus shift and forced churn segments. Correlate requested/selected page IDs, host bytes, H2D completion, slot reuse, event fences and valid answers.

3. Separate warm zero-fault performance from cold misses. Prove D2H seal cost and zero D2H on clean eviction; never manufacture nonzero counters as evidence.

4. Exercise rejection, cancellation/drain, single-slot sequential/queued client isolation, checkpoint restore and restart. Simultaneous multi-slot paging is optional until supported, not an automatic blocked requirement.

5. Sample RAM/pinned/VRAM/events/descriptors and queue depth through repeated cycles, with before/high-water/after plateau. Compare continuation after restore, not just HTTP success.

6. Use configurable segment/campaign durations, persisted checkpoints and progress, keep healthy tested runtime loaded. Record faults and true leaks with minimized reproducer and ownership for remediation.

## Concrete execution recipe

Read `EXECUTION_COOKBOOK.md` sections C2/C3/C4/C5 and `IMPLEMENTATION_CONTRACTS.md` sections I2/I5. These are shared context; reuse them within the cluster.

Build a segment manifest before execution: prepared-warm, known-cold promotion,
focus shift, sustained churn, rejection, cancel/drain, checkpoint/restore and
restart. Record release, hot cap, actual occupancy and duration/request IDs.
Prove occupied pages > observed hot capacity for pressure segments.

For at least one cold page correlate canonical checksum, host source, H2D event,
new slot/generation and attention use/answer. Distinguish D2H new-page seal from
clean eviction; zero traffic in warm focus is expected. A growing host catalog
during population is not automatically a leak: compare equal-work repeated
cycles after draining/releasing owned state.

Use the supported single slot with queued/cancelled clients; do not add a
two-slot requirement. Each completed segment is durable and resumable with
explicit warm/cache reconstruction after restart. Export per-segment correctness,
movement and resource plateau findings plus raw timelines; HTTP 200 alone
never satisfies a segment.

## Acceptance

## Failure routing and restart behavior

Read the smallest failing record and named source owner, state a falsifiable
hypothesis, change one causal variable, and rerun the minimized case before a
full matrix. Follow `BENCHMARK_PROTOCOL_V5.md` for sizing, capability probes,
progress-aware timeouts, provenance and resume. Repeated setup failure is not
quality evidence. Keep an attempt fingerprint and changed-variable list.
Do not copy a known failure into another giant handoff or silently downgrade
Turbo4, MTP, logical context or measurement protocol. If an unplanned prerequisite
is needed, add a bounded, fully specified task/dependency through the normal
assessment/state workflow, preserving current task order and completed evidence.
Do not renumber tasks just to reset the same exhausted retry.

For site lifecycle operations use passwordless `sudo -n`; capture exact runtime
identity and keep a healthy tested candidate loaded. Restore only for declared
controls or failed-start recovery. Never touch the unrelated service on 8092 or
kill unowned clients/runner display processes.
