# 21-04 — Harden benchmark preflight, progress, and fail-fast behavior

Recommended model: **Luna High**. Phase 21; cluster `21b-controls-soak`.
Depends on: `21-03`.

## Objective

Prevent another multi-hour campaign with an invalid route, tiny hotset, or
missing telemetry. Improve the benchmark tools rather than changing model
quality thresholds.

## Implementation

1. Extend `run-quality-corpus.py` and the shared benchmark contract with a
   preflight mode: one warm, one cold-needle, and one selected-all request.
   Validate all required telemetry before allowing a campaign.
2. Add explicit `--max-cases`, `--case-id`, `--case-index`, `--stop-after-
   failures`, and `--fail-fast-capability` behavior. Stop a mode after one
   startup/route/telemetry refusal or two same-prefix answer mismatches. Save
   a resumable checkpoint and classify unevaluated cases as not_run, never
   failed.
3. Use progress-aware per-request deadlines with a bounded default for
   preflight. A long campaign may opt into a larger limit, but a stalled
   request must emit its last progress and be resumable rather than consume
   the entire wall budget.
4. Require and serialize the effective argv, actual occupied tokens, hot-page
   budget, MTP placement, route, page/movement counters, and server/client
   timestamps in every record. Reject missing telemetry instead of coercing it
   to zero.
5. Add a compact report that distinguishes setup failure, capability refusal,
   quality mismatch, timeout, and valid measurement. Add regression tests for
   early stop and resume so a 24/48-case denominator cannot hide a failed mode.

## Acceptance

The preflight can be run independently in under a bounded diagnostic budget,
produces a complete envelope, and the corpus runner demonstrably stops and
resumes at the configured threshold. Create `handoffs/21-04.md` and
`evidence/PHASE21_HARNESS.json/.md`.

Do not run the full corpus while this task is being implemented. Keep the
successful candidate loaded and never touch port 8092.
