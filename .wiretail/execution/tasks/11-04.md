# 11-04 — Connect the dynamic hot-set controller to live table publication

## Objective

Turn retrieval and retention evidence into the next complete residency target using the runtime-derived
capacity, then publish it transactionally.

## Read

- Task README, cluster `11b-live-policy`, plan 21.3, 22 steps 4–5, 23.
- Handoffs 04-03, 08-03, 09-05, 11-01–11-03.
- Policy/replay, residency transaction, retrieval decisions, telemetry, host availability and server pin
  metadata.

## Implementation

1. Build one per-boundary trace from the immutable current table, live `H`, mandatory/recent/structural
   pages, retrieval results, observed telemetry, age/frequency, fault/dirty costs, and inflight pins.
2. Apply capacity-relative auto shares/minima and exact mandatory union. Reconcile rounding/deduplication
   deterministically to exactly `min(H,L)` target pages.
3. Keep retrieval score and retention score separate; record the reason for every add/keep/victim.
4. Convert delta to a residency transaction with host-source validation, victim reversibility, table
   generation fencing, and prior-table rollback.
5. Handle no telemetry, missing summary, mandatory overflow, dirty/all-pinned, and unavailable cold source
   through explicit safe behavior. Never silently reduce required context.

## Tests and live calibration checkpoint

Replay many capacities, ties, overlaps, unavailable evidence, focus persistence/shift, cold recall, pin
overflow, dirty victims, transaction failure, and stale inputs. Live calibration prompts must show stable
warm sets, cold-page additions, bounded churn, complete decision logs, and no capacity breach.

## Acceptance

Controller outputs are deterministic and capacity-correct; all required pages participate; live tables
change only after successful transfers/events; a failed update leaves the old graph-usable table.

Create `handoffs/11-04.md` with live decision examples, capacity reconciliation, faults, calibration
