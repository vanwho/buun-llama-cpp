## Objective

From a freshly compiled candidate and a freshly started server, load the
validated repository corpus to the 120,000-token safe frontier at logical
L=131,072 with H=51,200 (200 pages) selected GPU target KV. The 50K hot
geometry is mandatory, not a fallback ceiling: the occupied run must fill and
use the full configured hot window before extending into cold history. Keep target KV
and full-L draft KV Turbo4; draft KV must remain on GPU. Measure each prefill
chunk, GPU memory use/free, and the usual three canonical prompt MTP behavior
after the long history is resident. This is a repeatable 128K configuration
measurement, not a comparison of host-residency counters and not a claim that
all 131,072 tokens are occupied.

## Procedure

1. Capture a baseline `nvidia-smi` sample before stopping the old service.
After the fresh candidate is loaded, capture timestamp, total/used/free VRAM,
GPU utilization and power after model load, after full-L Turbo4 MTP allocation,
and after the first selected KV page is admitted. Also record server allocator
category values when exposed; missing optional pager/host residency telemetry
is not a failure condition.
   During the long fill, run exactly one task-owned sampler and append its
   output to the current raw root:

   ```bash
   nvidia-smi --query-gpu=timestamp,memory.total,memory.used,memory.free,utilization.gpu,power.draw --format=csv -l 1 >> /srv/ai/paged-kv/results/forward/102-05-128k/attempt-NN/gpu-memory.csv
   ```

   Stop only that sampler PID after the run; do not use a broad process kill.
2. Run the existing `run-occupancy-frontier.py` repo-content mode at exactly
L=131072, requested hot-page cap H=51200, page=256, B=1024/U=256, target
C=120000, one slot, and `max_tokens=400`, with chunks no larger than 16,000
fresh rendered tokens. Use the existing frozen fixture and schedule; do not
regenerate or change fixture contents. For attempt 01, run this zero-request
preflight and confirm `requests_sent=0`:

   ```bash
   python3 tools/server/bench/run-occupancy-frontier.py --output /srv/ai/paged-kv/results/forward/102-05-128k/attempt-01/occupancy --api-key-file /srv/ai/config/llama/api-keys --target-tokens 120000 --context-tokens 131072 --hot-tokens 51200 --page-tokens 256 --batch-tokens 1024 --ubatch-tokens 256 --slot-id 0 --max-fresh-tokens 16000 --max-tokens 400 --repo-content --preflight-only --wall-budget 7200 --prefill-timeout 900 --total-timeout 1200
   ```

   Then execute the frozen checkpoint without rebuilding its schedule:

   ```bash
   python3 tools/server/bench/run-occupancy-frontier.py --output /srv/ai/paged-kv/results/forward/102-05-128k/attempt-01/occupancy --resume-state /srv/ai/paged-kv/results/forward/102-05-128k/attempt-01/occupancy --api-key-file /srv/ai/config/llama/api-keys --target-tokens 120000 --context-tokens 131072 --hot-tokens 51200 --page-tokens 256 --batch-tokens 1024 --ubatch-tokens 256 --slot-id 0 --max-fresh-tokens 16000 --max-tokens 400 --repo-content --wall-budget 7200 --prefill-timeout 900 --total-timeout 1200
   ```

   Keep the final query/output/replay/MTP reserve below L and verify context
   shift/truncation are disabled. For retries, use a new `attempt-NN` only when
   candidate/source identity changed or the previous root cannot be resumed;
   otherwise resume the same checkpoint and never refill committed history.
3. Record for every successful prefill request: starting/ending committed C,
fresh rendered tokens, elapsed prefill time, tok/s, cached tokens, route,
request result, and timestamped VRAM used/free/utilization/power. Summarize
prefill tok/s by occupancy bands and keep the raw per-request journal. Slow but
forward-progressing chunks are measurements; continue the planned frontier.
If request progress stops or a real runtime error occurs, preserve the current
checkpoint, identify whether it is setup, capacity or code, fix the cause and
resume without discarding committed work.
4. H=51200 is mandatory for this and all later higher-context tests; never
   lower it to 16K or another value to make a row pass. On confirmed clean-
   start KV/scratch OOM, preserve logs, verify no prior Qwen process or CUDA
   allocation remains, and diagnose the actual memory ledger/configuration.
   Correct a mistaken candidate, stale process, ignored service override, or
   accounting setup while keeping L, H, B/U, model, codecs, MTP, threads and
   all other requested settings fixed. If genuine capacity cannot admit the
   full 200-page window, record this configuration as not admitted and do not
   relabel a smaller-H run as the required result or proceed to 102-06.
5. At C≈120000, add a narrowly scoped post-load helper after the occupancy
loop in `run-occupancy-frontier.py`, before its final result write. Copy the
final checkpoint's `state["messages"]` once to immutable `base_messages`; send
each probe as `base_messages + [{"role":"user","content":prompt}]` through
the existing request path. Do not clear/reload the slot and do not append probe
answers to `base_messages`, so all samples branch from the same occupied
prefix. Use the exact prompts from `forward/TESTING.md`: sorted-list Python
function, mmap-vs-read paragraph, and directory-watching Bash script. For each
prompt, request one 40-token warmup and three 400-token measured generations,
reasoning off. Save every request/response, actual output tokens and MTP
drafted/accepted counters; take slot-counter deltas immediately before and
after a request when the response lacks denominators. Report acceptance per
request and median per prompt. Preserve answer text; do not require exact
wording or exactly 400 generated tokens. Keep the 11,072-token L-C reserve and
do not permit compaction or context shift during this sequence.
6. Add one focused fake-client regression in `test_occupancy_frontier.py`
proving all 12 post-load requests reuse the same immutable occupied prefix and
retain per-request MTP deltas. Run that single test (plus the existing focused
occupancy test module only if helper integration requires it); do not run a
full test matrix or reload the server for a harness-only test.
7. MTP acceptance of 40% per prompt remains the reporting floor/goal, not a
reason to throw away a valid load run or block task 102-06. Report any miss
plainly with raw denominators. Correct Turbo4/GPU draft placement and a valid
request are required; a low acceptance percentage by itself is a finding.
