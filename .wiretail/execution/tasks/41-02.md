# 41-02 — Expose the explicit CPU-main-KV control boundary

Revision: `hotpath-v9-20260914`. Cluster: `41b-control-boundary-v9`.
Model: **Luna High**; first retry **Luna High**, same family.

## Objective

Make the phase-41 B1–B5 launcher able to run an explicit CPU-main-KV control
with GPU weights and GPU native MTP, using the existing `--no-kv-offload`
contract. The control must be distinguishable in its receipt from selected
packed and pager-off all-GPU profiles. Do not alter the production selected
route or claim a speedup until three fresh matched control samples exist.

## Required symbols and invariant

Audit `common_params_parse_ex`, `common_params::no_kv_offload`,
`common_base_params_to_speculative`, and the launcher profile construction.
The invariant is an explicit CPU-main-KV target (`no_kv_offload=true`) paired
with GPU weights and GPU native MTP, while the target/draft Turbo4 identity,
`L8192/H4096/A2048/B128/U64`, and committed-token accounting remain matched
across profiles. If the existing speculative projection intentionally changes
draft KV placement, expose that fact in the receipt rather than silently
calling it the required control.

## Fixture, before/after test, and stop condition

Use the original q0/q1/q2 prompts with fresh slots and the existing C6144,
128-committed-token B1–B5 setup. Before the change, demonstrate the launcher
cannot emit an explicit CPU-main-KV profile; after it, run the argument-parser
test and a dry-run/profile assertion that records `--no-kv-offload` and GPU
native-MTP independently. Stop and retain a null CPU speedup if any profile
cannot prove its KV placement or if the three controls are not matched.
