# 83-03 — Freeze a stable native-MTP and pager diagnostic matrix

Revision: `hotpath-v10-20260914`. Cluster: `83c-benchmark-v10`.
Model: Luna High; first retry High. Prerequisite:83-02.

Do not run the broad three-prompt speed matrix yet. First establish one
reproducible diagnostic coordinate that can distinguish a common model/output
failure from an MTP state failure and from a selected-pager route failure.

1. Check `sudo -n true`, acquire the canonical benchmark lifecycle lock, stop
   only the named Qwen service when required, and build or select one immutable
   candidate. Record the source SHA, executable SHA, model SHA, loaded PID and
   complete effective command line in the raw root before sending a request.
   A stale endpoint or a binary different from the recorded bundle invalidates
   the row; do not continue under a relabeled identity.
2. Use q0 only, seed 42, temperature 0, thinking disabled, the installed
   Qwen3.8-27B UD-IQ4_XS model, and a bounded 64-token completion. Run one
   short C≈256 control and one exact cached-prefix C≈6143 coordinate. Use one
   warmup and one measured request per row; this is a diagnostic matrix, not a
   statistical performance claim. Save rendered token IDs, raw SSE, response
   JSON, journal acceptance lines, `/metrics` before/after snapshots, and slot
   snapshots for every row.
3. Run these placements with the same request body and output settings:
   all-GPU feature-off; all-GPU native MTP; CPU-main-KV with GPU native MTP;
   selected pager with native MTP; and selected pager feature-off. Native rows
   must use target Turbo4 K/V, draft GPU Turbo4 K/V,
   `--spec-type draft-mtp`, positive `--spec-draft-n-max`, and the canonical
   request-scoped draft/accepted counter deltas. Feature-off rows are controls,
   never MTP evidence.
4. For each native placement attempt B=U=128 first. If it cannot start because
   of capacity or shape, retain that failure and run one explicitly labelled
   B=128/U=64 secondary row at the same L/C so capacity/shape failure is not
   confused with MTP-state failure. If U128 starts and produces positive draft
   work, repeat the same row at U64 as a causal secondary. Keep the two
   geometries in separate raw roots and reports. Do not silently substitute
   U64 for the primary U128 diagnostic; the earlier high-acceptance evidence
   used U128 while the recent zero-acceptance evidence used U64.
5. Classify output independently of paging: compare the feature-off greedy
   target token IDs with native-MTP target output for the first 32 generated
   tokens. If feature-off is also slash/corrupt, classify a common model,
   template, sampling, or quantization problem. If only native rows diverge,
   classify an MTP draft/target state or rollback problem. If only selected
   rows diverge, classify a pager route, page-table, or cold-page problem.
   Never infer correctness from HTTP 200 or a non-empty response.
6. Report, per row, startup placement, B/U, L/C/H/A, draft and accepted token
   deltas, acceptance percentage, first divergent token position, finish reason,
   route counters for prefill/decode/MTP verification, graph rebuild/replay,
   faults/evictions, H2D/D2H, waits, and the exact failure boundary. A zero
   accepted count with positive draft work is a real zero result; missing
   counters are setup failure and must be rerun after fixing observation.

Do not infer C, H, A, or MTP acceptance from launcher arguments. Do not force a
page ID, add a second attention pass, or change route policy in this task.
Capture the smallest reproducible matrix that later tasks can use to repair
MTP and paging without spending another long occupancy run.

Required proof: `phase83_stable_mtp_matrix`.
