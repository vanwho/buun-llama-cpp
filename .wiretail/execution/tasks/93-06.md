# 93-06 — Repair selected prompt-trim recovery after rejection

Any successor tasks must carry the same exact model and assessment pins.

## Objective

Remove the selected/paged prompt SIGSEGV recorded in 93-04. The failure begins
when the partial suffix removal logs `memory_seq_rm [p0, end) rejected`, then
the server attempts a full target/draft reset. Make that path return either a
coherent retry from empty state or a clean failed request with the slot
released; it must never continue with target and draft at different frontiers.

## Work

1. Start from the 93-04 raw server log and identify the exact rejecting call,
   whether target or draft rejected, whether either call mutated state before
   returning false, and the first crashing operation after the warning. Record
   this short call sequence in the handoff before editing.
2. Trace how a trim rejection reaches the full reset and how that reset clears
   target memory, draft memory, speculative backup/rewind state, token ledger,
   prompt statistics, checkpoint deliveries, and cache-plan deliveries.
   Determine which invariant is violated at the SIGSEGV site.
3. Make the smallest code change at the owning seam. A failed partial trim
   must not be treated as success. If a partial trim can mutate one side before
   the other fails, run a coordinated recovery that clears both sides with a
   documented supported API, retires speculative backup state, invalidates
   checkpoints/cache-plan delivery and zeros the slot's cached-token ledger.
   If coherent reset cannot be proven, fail and release the request/slot before
   another decode. Do not assert on an expected `false` result, dereference
   state invalidated by reset, or silently continue from stale positions.
4. Preserve the successful dense MTP path and the fast automatic selected
   dense/direct/packed routes. Do not fix this by disabling MTP, forcing CPU,
   falling back to `selected_reference`, or changing the acceptance threshold.
5. Add a focused regression hook at the memory/server seam so task 93-07 can
   deterministically exercise the rejection without relying on an accidental
   allocator failure. Keep any failure injection test-only; do not add a
   production environment toggle or per-token diagnostics.
