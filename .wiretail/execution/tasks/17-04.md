# 17-04 — Repair dynamic VRAM admission for Turbo4 target and MTP

## Objective

Make native MTP startup fit the available device without hard-coded context or
hotset assumptions. The target is Qwen3.8-27B UD-IQ4_XS on the available
machine, but the implementation must remain generic.

## Read

- Cluster `17b-mtp-capacity`, handoff 17-03, phase-15 MTP-fit work, allocator
  and context initialization code, and current profile/benchmark evidence.

## Work

1. Trace the native-MTP allocation failure where an 82.01 MiB allocation was
   attempted with approximately 67.8 MiB free.
2. Jointly account for model weights, graph/scratch buffers, target Turbo4 KV,
   context-sized draft Turbo4 KV, VMM granularity, staging, routing metadata,
   and an explicit safety headroom.
3. Derive target and draft rows from the resolved request context. Do not use a
   fixed 77K value, silently shorten the request, or make draft KV a pager
   victim.
4. Permit fit-aware batch/ubatch and layer decisions for acceptance probes;
   report the resolved values and reject impossible requests explicitly.
5. Make the admission result machine-readable with requested, resolved,
   accepted, and refusal reasons.

## Acceptance

Run a dynamic context ladder from small/all-pages-fit through intermediate,
odd-tail, and the largest feasible context. Prove native MTP remains Turbo4 and
GPU-resident, target pager capacity is ledger-derived, and an impossible request
fails before a restart loop. Use deterministic allocator tests and a
 live Qwen smoke when the service can be isolated.

## Deliverable

Create `handoffs/17-04.md`, portable admission/ledger changes, focused tests,
and raw startup evidence.
