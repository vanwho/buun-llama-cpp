# 106-01 — Build latest fork master and measure GPU-only controls

Use `forward106-master-baselines` as the complete protocol. This task owns
the first clean master build, the original empty-context GPU-only benchmark,
and the matched GPU-only context series. It begins only after the separate
106-00 ACO promotion-cost prelude. Do not rerun 106-00 and do not use the ACO
branch binary for these master controls.

## Build and freeze first

1. Acquire `/tmp/ai-pager-benchmark.lock`. Confirm only the intended GPU
   workload can run; stop the existing managed Qwen owner through its
   noninteractive managed lifecycle and verify its CUDA allocation is gone.
   Do not start an additional Qwen process.
2. Fetch the fork's latest master exactly once with
   `git fetch origin master`. Record `git rev-parse refs/remotes/origin/master`
   as `master_commit`. Create a detached worktree at that SHA under
   `/srv/ai/paged-kv/worktrees/master106-<12-char-sha>`; confirm it is clean.
3. Configure a new build directory
   `/srv/ai/paged-kv/builds/master106-<12-char-sha>` with
   `cmake -S <worktree> -B <build-dir> -DCMAKE_BUILD_TYPE=Release -DGGML_CUDA=ON -DCMAKE_CUDA_ARCHITECTURES=89-real -DGGML_CUDA_FA=ON -DGGML_NATIVE=OFF -DLLAMA_BUILD_TESTS=ON`,
   then build with
   `cmake --build <build-dir> --parallel 16 --target llama-server`.
   Never use `--clean-first` on a just-created build tree. Keep full configure
   and build logs outside Git.
4. Verify `llama-server --version`, CUDA device support, target Turbo4,
   `draft-mtp`, draft Turbo4 and GPU placement options using this binary's
   `--help`; inspect model SHA, executable hash and every loaded project DSO
   hash. Record GPU/driver identity and exact expanded argv template in
   `.wiretail/execution/evidence/MASTER106_FREEZE.json/.md`. No request is
   allowed until the CLI accepts the complete fixed argv below and startup
   log inspection can verify Turbo4 target KV, GPU Turbo4 draft KV, and
   `n-max=2`. If an upstream option is named differently, resolve it from
   this build's help/source, update the freeze once before any measured row,
   and use that one corrected invocation for all rows. Do not probe with a
   one-token request.

Before the first filled row, use the cluster's benchmark-driver requirements.
If needed, implement `tools/server/bench/run-master-context-matrix.py` using
`repo_context.py` for the frozen A/B/A plus repository-source fill and
`run-final-curve.py` for canonical request/SSE/MTP parsing. Add only its three
specified deterministic regression cases. Do not use the selected-only
`run-occupancy-frontier.py` as the scored matrix driver unchanged. This helper
must support both placements so 106-02 reuses the same frozen source schedule,
rendered request bytes, snapshot restore, and output parser.

## Exact GPU-only server command

Use the same command for each row, changing only the explicitly listed `-c`
value and the result directory. The server has no pager/hot-cache options:

`<BUILD_DIR>/bin/llama-server -m /srv/ai/models/text/current.gguf --alias qwen38-fast-turbo4-mtp -ngl 999 --device CUDA0 --fit off -fa on -c <L> -np 1 -ctk turbo4 -ctv turbo4 -b 1024 -ub 256 --poll 0 --host 0.0.0.0 --port 8080 --api-key-file /srv/ai/config/llama/api-keys --metrics --reasoning-preserve --no-context-shift --spec-draft-kv-device gpu --spec-type draft-mtp --spec-draft-n-max 2 --spec-draft-type-k turbo4 --spec-draft-type-v turbo4`

Do not add `--kv-pager`, `--kv-hot-pages`, selected/reference route, or
CPU-offload flags. Start the managed service from this exact binary using the
site lifecycle/allowlisted benchmark environment; record the actual process
argv and loaded DSOs, not only the intended command.

## Required run order

First run the original unfilled baseline at `L=77,824`, `C=empty`. Run the
fixed 48-request schedule: 3 prompts × 4 reasoning modes × (one 40-token
warmup + three measured 400-token-maximum SSE requests), T=0, seed 42. Record
the three median tables and per-prompt raw rows. This baseline must precede
any context fill.

Then run four separately configured, clean-start filled rows in this exact
order: `(L=8,192,C=6,144)`, `(L=16,384,C=14,336)`,
`(L=32,768,C=30,000)`, `(L=65,536,C=61,440)`. The 8K row matches the former
8K/4K ACO test's total occupancy; it has no 4K hot limit because this is
GPU-only. For every row:

1. Stop the prior row's server and verify its process and GPU allocations are
   gone; start the exact master binary fresh with the row's `-c`.
2. Load the frozen `repo-context-v1` A/B/A seed and selected tracked-repository
   source schedule from an empty slot in bounded chunks. Append at most 4,096
   fresh tokens per request. Record
   cumulative C, fresh token count, elapsed prefill, fresh tok/s and raw
   request/response at every append; report curve points near each reached
   8,192-token boundary. No cached-token rate may be labeled fresh prefill.
3. Stop at the exact C in the cluster table. Verify the next canonical
   prompt, 400-token maximum response, and MTP replay fit while retaining at
   least the cluster's 1,536-token safety reserve. Freeze the filled base and restore it
   independently before every canonical request.
4. Run all 48 canonical requests. Save raw request/SSE files outside Git;
   calculate medians from the three measured repetitions only. A setup
   mismatch is repaired here and the incomplete row resumed; low speed, low
   MTP acceptance, or incomplete request-local MTP telemetry is reported
   without inventing values or retrying an already completed request.

Write one compact row report per L/C, with DECODE MEDIAN TOK/S, MTP
ACCEPTANCE MEDIAN %, and FRESH-PREFILL MEDIAN TOK/S tables, plus the
incremental context-fill curve. Include process/build/model identity and
full effective argv in every row. Save raw files only under
`/srv/ai/paged-kv/results/forward/106-master/106-01/`.
