# 02-03 handoff

## Outcome

Added a separate bounded KV residency pool and asynchronous transfer seam.
Transfer plans retain page/table epochs and coalesce only compatible
layer/side/physical-row runs. H2D promotions reserve destination slots and
events before mapping or submission; D2H sealing/resealing reserves host
catalog capacity before submission. Completion callbacks receive the full
logical page, generation-bearing identity, physical slot, table epoch, and run
index. Stale completion or any copy/map/cancellation failure rolls back newly
mapped slots and releases reservations without publishing a partial table.

Clean host-valid eviction is a slot drop only and does not call the copy
callback. Dirty mappings are refused until the caller reseals and clears the
dirty state.

## Invariants/evidence

- The fake backend covers H2D mapping, bounded pinned-ring upload, asynchronous
  completion, D2H completion into bounded ring staging, catalog reservation,
  generation/table recheck, and useful/aligned byte accounting.
- Injected catalog admission, destination mapping, submit, completion, and
  stale-recheck failures leave no mapped-slot, pending-event, pinned-ring, or
  fake-backend pending-copy leak.
- Cancellation callbacks are idempotent at the adapter boundary; when a
  backend has no explicit cancel operation, completion is used as the fence
  before resources can be reclaimed.
- Transfer counters are fixed scalar fields: queued, submitted, useful and
  aligned bytes, waits, cancellations, stale completions, event completions,
  and evictions. No full-context or full-store transfer vector is created.
- The existing VBR VMM pool remains representation-owned. The new pool shares
  the bounded pinned-ring/event transport helpers but owns only residency slots
  and logical mappings.

## Remaining risks

- The pool is intentionally a production callback boundary until the later
  device integration supplies concrete slot/VMM operations. Callers must keep
  the catalog reservation after a successful D2H commit and must not publish a
  residency table until their transaction recheck succeeds.
- D2H bytes are handed to the catalog sink after each completed run; the sink
  must treat this as staged data until the 02-04 transaction publishes the
  complete residency update.
