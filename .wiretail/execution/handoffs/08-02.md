# 08-02 handoff

## Outcome

Native MTP capacity now follows the realized target per-sequence context for
fit projection, startup, and server recreation. The trained-context frontier
is no longer used as an MTP allocation floor, and the cache-budget input no
longer supplies an implicit numeric MTP row count.

## Code paths

- `common_speculative_mtp_context_params_resolve()` is the shared geometry
  helper. Native callers pass `native_mtp=true`; omitted `-cd` resolves to
  `llama_n_ctx_seq(ctx_tgt)`, matching explicit `-cd` is accepted, and a
  mismatch returns the typed `conflicting_explicit_context` status.
- `common/common.cpp` and the server fit-swap path mark implicit native MTP as
  following each target candidate's per-sequence context. Explicit values are
  projected as fixed values and checked again against the authoritative target
  before context construction.
- `common/speculative.cpp` and
  `tools/server/server-context.cpp` use the resolved target sequence width for
  native startup and recreation. Rejection occurs before
  `llama_init_from_model()` for a conflicting native `-cd`.
- External MTP sidecars continue to use the non-native helper mode, preserving
  independent explicit `-cd` and KV topology.
- Native MTP keeps `--spec-draft-kv-device` independent of target
  `--no-kv-offload`; GPU placement is required when requested, Turbo4/Turbo4
  is required, and the realized memory breakdown is fail-closed unless every
  nonzero context allocation is on a GPU/IGPU backend.
- Residency logging reports rows, bytes, bytes/token, backend device, and the
  static `mtp_gpu_reserved` budget category. MTP VBR/pager controls are cleared
  by the shared apply helper.

## MTP allocation logs and raw paths

The production log format is emitted by
`common_speculative_mtp_log_residency()` and includes `rows=`, `bytes=`,
`bytes_per_token=`, `backend=`, and `budget_category=mtp_gpu_reserved` for
each realized MTP context-memory buffer, followed by a committed summary.
No model-backed MTP startup log was captured in this workspace: the available
GGUF files are vocabulary-only fixtures, not target/draft model weights.
There is therefore no raw live-log path to retain for this task.

## Deferred verification

Run later with a native-MTP target/draft GGUF pair and the built
`build-cuda/bin/llama-server` on the available CUDA GPU. Exercise three target
contexts, including the maximum accepted context, across `--spec-draft-kv-device
auto|gpu|cpu`, target GPU/CPU KV, target `--no-kv-offload`, and the supported
single/multiple-slot topologies. Retain startup and teardown logs and verify:

1. native MTP `rows` equals target `llama_n_ctx_seq` at every context;
2. K/V types are Turbo4/Turbo4 and every MTP context buffer reports a GPU/IGPU
   backend, including target `--no-kv-offload` with draft KV device `gpu`;
3. mismatching native `-cd` fails before partial MTP context creation;
4. MTP bytes are charged once as static `mtp_gpu_reserved` and teardown
   releases the reservation.

## Remaining risks

The local unit/build checks do not substitute for model-backed CUDA startup,
maximum-context memory pressure, live placement inspection, or teardown
accounting. Those checks remain deferred because the required model weights and
raw runtime-log capture are unavailable here.
