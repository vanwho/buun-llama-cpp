## Diagnostics and result

The `compute-sanitizer --target-processes all --attach <pid>` attempt could
not attach to the managed service because it had not been launched in an
attachable mode. The distinct alternative succeeded: an opt-in
`GGML_CUDA_TRACE_NODE_SYNC=1` diagnostic synchronizes after each CUDA graph
node and reports the first failing GGML operation. The diagnostic source edit
is in `ggml/src/ggml-cuda/ggml-cuda.cu` and was included in the immutable
candidate.

Canonical command:

```text
python3 tools/server/bench/run-mtp-diagnostic.py --output /srv/ai/paged-kv/results/v10/93-11d/attempt-01/diagnostic-node-sync --model /srv/ai/models/text/Qwen3.8-27B-UD-IQ4_XS.gguf --server-binary /srv/ai/paged-kv/results/v10/93-11d/attempt-01/diagnostic-candidate-bundle/llama-server --endpoint http://127.0.0.1:8080 --key-file /srv/ai/config/llama/api-keys --context 8192 --batch 128 --ubatch 64 --n-predict 16 --draft-n-max 2 --repeats 1 --startup-timeout 180 --request-timeout 300
```

The run used graph disabling plus per-node synchronization. Dense MTP-off,
dense native MTP, and selected-resident native MTP passed. Cold A passed. The
1760-token cold B append timed out at 300 seconds after checkpoint restore and
`CHECKPOINT_ATTN_ONLY_TRIM p0=27 target=1 draft=1`; cold A again did not finish
because the service encountered the CUDA fault.

At 08:48:13 CEST, after all earlier nodes had synchronized successfully, the
first failing node was:

```text
op=FLASH_ATTN_EXT name=node_232 type=f32 ne=[256,24,64,1]
error=an illegal memory access was encountered
```

The log currently prints node and src0/src1 addresses, but not enough tensor
metadata to prove which key/value/page backing identity is invalid. The
available trace therefore identifies the failing operation but does not
justify changing a particular kernel or VBR lifetime owner. The failure and
regression work are scheduled to 93-11e before 93-12; 93-12 remains `todo` and
depends on 93-11e.
