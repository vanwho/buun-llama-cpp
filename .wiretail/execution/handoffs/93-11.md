# 93-11 handoff — Empty selected-route suffix trim repair

## Reproduced defect and owner

The 93-10 selected-resident request was the native-MTP paged-resident rung
`03-mtp_on_selected_paged_resident`, using the canonical short completion with
30 incoming tokens. Its `server.log` recorded
`edit/divergence sample (cached/incoming/lcp/reusable/rewind/append/cache_prompt) = (0/30/0/0/0/30/1)`, then
`prompt suffix trim rejected (target=0 draft_attempted=0 draft=0); full reset target=1 draft=1`,
then systemd reported `status=11/SEGV`. The immutable candidate and event hashes
are recorded in `V10_93-10.json`; the run-config pinned the selected route,
model, executable, context, and Turbo4 GPU MTP setup.

Expected behavior: with no resident target or draft sequence rows, trimming the
suffix beginning at prompt position 30 is a successful no-op. No paired reset
should occur. The owning production code is the target/draft trim lambdas in
`server-context.cpp`, passed to `server_prompt_trim_recover`.

## Repair

Added `server_prompt_trim_has_suffix(first_removed, last_present)` and used
`llama_memory_seq_pos_max` in both trim lambdas. A trim API is called only when
the requested start is at or before a resident position. Empty target memory
therefore no longer turns a no-op into trim rejection and destructive paired
recovery; draft trim still runs independently when its own suffix exists.

Added a deterministic fake in `test-server-prompt-cache.cpp` for position 30
with empty target and draft memories. It checks that neither memory removal nor
recovery/reset runs, the prompt ledger remains intact, and a suffix at position
30 is still recognized when present.
